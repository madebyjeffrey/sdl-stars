# Win32 window positioning over SDL3

The positioning milestone reached **118/178 inventoried Win32 APIs (66.3%)**, up from
117/178 (65.7%). This batch adds `SetWindowPos` and expands window creation,
movement, default message handling and sibling traversal. Six CRT helpers are
counted separately. These are implementations of documented subsets; the full
Linux game UI still does not link, and this is not a claim of complete Windows
compatibility.

Current coverage is **124/178 (69.7%)** after the [input milestone](WIN32-INPUT.md).

No additional packages are required.

## Build and debug in CLion

Reload the SDL CMake profiles and select **stars-compat-position** in
`sdl-debug` or `sdl-release`. Set
`SDL_VIDEODRIVER=dummy;STARS_SDL_RENDERER=software` for the deterministic test.
The executable exits after checking its contracts. The CTest case sets those
variables automatically.

```sh
cmake --preset sdl-debug
cmake --build --preset sdl-debug
ctest --test-dir dist/sdl-debug -R 'win32_position|win32_abi' --output-on-failure
```

Useful breakpoints are `SetWindowPos`, `ReorderCompatWindow`,
`DefWindowProcA` and `FComposeChildren`. The `WINDOWPOS` structure now has
shared native/SDK size and offset assertions (40 bytes on the validated 64-bit
ABI; `x` at offset 16 and `flags` at 32).

The shared SDK test builds as `test_win32_position_reference`:

```sh
cmake --preset mingw-debug
cmake --build --preset mingw-debug
xvfb-run -a env WINEDEBUG=-all ctest --test-dir dist/mingw-debug \
  -R 'test_win32_position_reference|test_win32_abi_reference' \
  --output-on-failure --timeout 60
```

## Implemented behavior

`SetWindowPos` delivers `WM_WINDOWPOSCHANGING` with a writable request, applies
its adjusted coordinates, dimensions, flags and sibling placement, then delivers
`WM_WINDOWPOSCHANGED`. The request's target HWND cannot be redirected by changing
that structure. Destroying the target during either callback is guarded;
recursive positioning leaves the most recent committed geometry intact.

Default processing of `WM_WINDOWPOSCHANGED` delivers `WM_SIZE` and `WM_MOVE` for
changed dimensions/position. An application that handles the changed message
without passing it to `DefWindowProc` suppresses those derived messages. Default
processing of `WM_WINDOWPOSCHANGING` queries `WM_GETMINMAXINFO` for resizable or
overlapping top-level windows and clamps the proposed dimensions to the returned
tracking limits. The game's UI handlers for those limits can therefore adjust
programmatic resizing. Complete native nonclient sizing and interactive tracking
policy remain separate work.

`MoveWindow` now uses the same positioning path. Repainted moves call
`UpdateWindow`; moves with repaint disabled preserve the no-redraw contract.
Zero/negative dimensions are accepted and normalized to zero. A zero-sized child
has an empty logical client area and receives no pixels; the drawing backing
surface uses a minimum allocation of one pixel so DC lifetime remains valid.
SDL also requires a minimum physical root size of one pixel, while the wrapper
reports the requested zero logical dimensions. Queued physical resize events
preserve that distinction, including older events overtaken by a newer zero-size
request. SDL window movement events now generate `WM_MOVE`.

Sibling chains are separate from the handle registry. New children start at the
bottom, and top-level windows start above other ordinary windows. Explicit top,
bottom and sibling-relative placement updates `GetWindow`, child composition
and mouse hit testing together. Hidden siblings retain their position in the
chain. Topmost/ordinary root bands preserve owned windows above their owners.
Promotion/demotion updates `WS_EX_TOPMOST`, including owned families. Newly
created owned windows inherit their owner's topmost status. Creation also accepts
`WS_EX_TOPMOST` directly; other extended styles remain unsupported.

| Flag | Implemented effect |
| --- | --- |
| `SWP_NOMOVE`, `SWP_NOSIZE` | Retain current coordinates/dimensions, ignoring the corresponding arguments. Callbacks may change these flags. |
| `SWP_NOZORDER` | Ignore the insert-after argument and preserve sibling order. |
| `SWP_NOREDRAW` | Leave existing presentation pixels and update regions untouched until explicit drawing/invalidation. |
| `SWP_SHOWWINDOW`, `SWP_HIDEWINDOW` | Change visibility without the `WM_SHOWWINDOW` notification generated by `ShowWindow`. |
| `SWP_NOACTIVATE` | Suppress this operation's explicit root focus/raise request. OS focus policy can still generate events independently. |
| `SWP_NOOWNERZORDER` | Keep the owner in place when positioning its owned window, subject to the invariant that owned windows stay above their owners. |
| `SWP_NOSENDCHANGING` | Suppress the changing callback; the changed callback still applies when state changes. |

The supported flags include every flag currently used by Stars' `SetWindowPos`
call sites. Other flags return failure with `ERROR_INVALID_PARAMETER` instead of
silently claiming support. Frame/nonclient recalculation, no-copy-bits and deferred
position batches remain to do. Window operations beyond this API do not yet
consistently supply Win32 last-error values.

## Platform constraints and reference differences

Sibling ordering for logical children is fully controlled by the runtime. For
independent SDL desktop windows, the model retains the requested ordering and
SDL requests topmost status and activation/raising. Exact sibling-relative desktop
stacking, foreground focus theft restrictions, and visibility/activation effects
remain subject to the window manager and SDL backend. Arbitrary desktop stacking
without activation is not yet reproduced. These constraints do not affect the
logical child compositor.

The compatibility windows currently require X11 (or Xwayland), or SDL's dummy
backend for tests. Unlike the direct SDL smoke test, root creation in this layer
requests an explicit position and fails if that backend rejects it. Pinned SDL's
Wayland implementation rejects positioning non-popup windows; native Wayland
root/popup adaptation remains unqualified work. In a Wayland desktop session,
use `SDL_VIDEODRIVER=x11` for these compatibility application targets when
Xwayland is available. This limitation was established from the pinned backend
source; Xvfb tests do not verify Wayland behavior.

Geometry still uses client-sized surfaces; Windows nonclient borders, caption
sizes, menu exclusion and DPI virtualization are not reproduced. Most shared
geometry comparisons therefore use borderless popup windows. The tracking-limit
test compares outer rectangles rather than equating thick-frame client areas.

Wine 9.0 promotes an existing owned popup when asked to promote its owner, but
leaves the owner ordinary; demoting that owner also leaves the popup topmost in
this test. An independent window promotes/demotes correctly. The same family
difference occurs in a private, managed Wine virtual desktop, so it is not simply
an absent Xvfb window manager. The reference test reports that exact Wine pattern;
on an actual Windows runtime the owner-family assertions remain strict. Native
checks assert both family flags and relative placement. This follows Microsoft's
[SetWindowPos documentation](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowpos),
which specifies topmost promotion/demotion effects on owned windows.

Callback and default-message contracts follow
[WM_WINDOWPOSCHANGED](https://learn.microsoft.com/en-us/windows/win32/winmsg/wm-windowposchanged)
and [MoveWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-movewindow).
SDL's [SDL_RaiseWindow](https://wiki.libsdl.org/SDL3/SDL_RaiseWindow) documents
window-manager control of focus/raising. The implementation was also checked
against this project's pinned SDL 3.4.18 headers.

## Verification scope

`tests/compat/win32_position.c` checks move-only/size-only calls, callback edits,
callback suppression, unchanged requests, top/bottom/sibling order, visibility,
zero/negative sizes, recursive positioning and callback-driven destruction. It
also checks independent topmost bands, ownership/inheritance, root geometry and
minimum/maximum-size callbacks. Native-only checks verify presentation order,
restoration after a no-redraw move, preserved update regions, zero-area DC
clipping and normalized SDL move/resize messages.

The existing window, child, GDI, resource, font and other compatibility tests
remain part of the checks. The Windows game and Linux host do not link the SDL
runtime, and no game logic, record layout or regression fixture was changed.

## Toolbar and tooltip placement

`ExecuteButton` obtains the left edge and bottom of the toolbar item from
`ToolbarWindow32` through `TB_GETRECT`. Minefield, design, enemy
class and zoom menus no longer depend on where inside the item the mouse clicks.
Other context menus keep their original cursor positioning.

`TooltipWndProc` places each tooltip two pixels below its associated screen
rectangle, clamps its width within the frame, and moves above the control when
there is insufficient room below. On native SDL backends the `starstt` class
uses `SDL_WINDOW_TOOLTIP`, parented to the owning root window; `SetWindowPos`
converts its logical screen coordinates to SDL owner-relative coordinates.
Tooltips are nonactivating. The dummy driver retains logical top-level windows.

The actual-client Continue Game test checks all four toolbar popup anchors,
then shows a tooltip from two different points inside the same control. It
checks stable placement, unchanged focus, and the native tooltip parent/role.
The button painting test checks the selected radio dot's white corner and black
center pixels. These are UI changes; save layouts and turn results are unchanged.
